# 《德国心脏病》数字实现方案

## 1. 范围与原则

首版目标是在 `game-hall` 插件 API v1 上实现 2-6 人、服务端权威、支持实时抢铃和重连的经典水果版 Halli Galli。默认使用 AMIGO v3.1 的 `official_last_bell` 终局，另提供说明书允许事先约定的 `complete_collection` 延长玩法。

核心原则：

- 服务端保存完整牌序、每个明牌堆和动作受理次序；客户端只接收当前可见顶牌与数量。
- `flip_card` 是当前翻牌者的顺序动作，`ring_bell` 是所有合资格玩家随时可提交的竞争动作。
- 同一房间的动作在单一互斥锁／事务中串行化；同一桌面版本只结算一次铃。
- 不信任客户端传入的命中结果、卡牌、时间戳、延迟、赢家或分数。
- 洗牌、余数发牌与任何自动裁决只使用服务端 RNG；测试可注入固定种子。
- 每次状态修改原子完成并递增 `revision`；每次改变可见顶牌或清桌再递增 `boardEpoch`。
- 规则档案、时间参数与公平模式开局后锁定并写入战绩。

## 3. 规则档案

`model/rules-profiles.json` 是房间规则唯一来源。

### 3.1 `official_last_bell`

- 当前官方短终局，作为默认。
- 在局人数完整结算后降到 2 时设置 `finalDuelArmed=true`。
- 该标记已经为真时，下一次被服务端受理的铃结束游戏。
- 正确铃由按铃者先收全部明牌；错误铃由对手收全部明牌。
- 统计总持牌数，最高者获胜，平手共同获胜。

### 3.2 `complete_collection`

- 说明书允许事前约定的延长玩法。
- 不使用最终二人铃；一名玩家持有全部 56 张牌时结束。
- 仍启用 `no-progress` 安全阀，避免数字房间永久停滞。

两种档案使用同一 56 张牌和 `exactly 5` 抢铃谓词，不得在局中切换。

## 4. 权威领域状态

`model/game-state.schema.json` 是持久化和重连边界。运行时可以使用 dataclass，但字段语义应保持一致。

### 4.1 整局字段

- `gameNumber`：再来一局时递增。
- `profileId`：锁定的规则档案。
- `phase`：`waiting | playing | resolving_bell | finished`。
- `revision`：任何成功的权威状态变更递增一次。
- `boardEpoch`：只在可见顶牌改变或全部明牌被清走时递增。
- `players`：固定座次、抽牌堆、明牌堆、连接和资格状态。
- `currentPlayerId`：下一名应翻牌的合资格且抽牌堆非空玩家。
- `lastFlip`：最后一次翻牌的事件、玩家、卡牌和服务端时间。
- `fruitTotals`、`validFruitIds`：由各明牌堆顶牌派生的缓存；每次事务后独立复算验证。
- `finalDuelArmed`：默认档案的最终铃门闩。
- `bellResolution`：最近一次铃的判定、桌面版本、赢家／误按者和收牌数。
- `result`：结束原因、各玩家牌数和胜者。
- `events`、`eventSeq`：公开审计事件；实时视图只下发有限窗口。
- `rng`：服务端私密随机状态与承诺，绝不进入客户端视图。

### 4.2 玩家字段

- `id`、`seat`、`displayName`、`connected`。
- `status`：`eligible | eliminated | resigned`。
- `drawPile`：有序卡牌实例 ID，数组首项定义为下一张。
- `discardPile`：该玩家的明牌堆，按最早到最近的顺序保存，末项是唯一参与计数的顶牌。
- `eliminationReason`：`null | discard-captured | wrong-bell-empty | resigned`。
- `lastActionSeq`：调试和重连用，不参与赢家判定。

抽牌堆为 0 不等于 `eliminated`。只要 `discardPile` 非空且没有误按，该玩家仍为 `eligible`，只是不会成为 `currentPlayerId`。

## 5. 卡牌实例与区域守恒

牌种目录定义 20 种唯一牌面。每局展开为 56 个稳定实例 ID，例如：

```text
banana-1-01 ... banana-1-05
banana-2-01 ... banana-2-03
...
plum-5-01
```

每张实例必须且只能出现在一个玩家的 `drawPile` 或 `discardPile`。`resolving_bell` 可以在事务局部变量中暂存收牌，但提交后的序列化状态不保留公共中转区。

收牌的确定顺序为：从铃赢家座位起顺时针枚举玩家；每堆按数组顺序（最早到最近）追加到赢家 `drawPile` 末端。官方未规定实体收牌手势，此裁决使回放和固定种子测试稳定。

## 6. 状态机

完整机器可读表见 `model/state-machine.json`。

1. `waiting`：等待宿主达到人数并开局。
2. `playing`：当前顶牌可见；接收当前玩家的 `flip_card`，也接收任意合资格玩家的 `ring_bell`。
3. `resolving_bell`：持有房间锁，冻结新翻牌；原子判断、收牌或罚牌、更新资格与终局。
4. `finished`：只读结果；只能走宿主公共再来一局流程。

`resolving_bell` 通常在一次 `act()` 内完成，前端未必会收到这一瞬时阶段，但把它显式建模有助于事务日志和故障恢复。

## 7. 动作协议

所有动作都必须验证房间成员、玩家资格、阶段、负载结构和版本。拒绝动作不得产生部分状态修改。

### 7.1 `flip_card`

```json
{
  "revision": 18,
  "expectedBoardEpoch": 12
}
```

校验：

- 当前阶段是 `playing`；
- 调用者等于 `currentPlayerId`；
- 调用者 `status=eligible` 且抽牌堆非空；
- `revision` 和 `expectedBoardEpoch` 与服务器一致；
- 已达到公平档案规定的 `earliestNextFlipAt`。

事务步骤：从 `drawPile[0]` 移到本人 `discardPile` 末端，记录公开翻牌事件，递增 `boardEpoch`，复算水果合计，选择左侧下一名有牌可翻玩家，并设置新的最早翻牌时间。

翻牌后不自动判断正确铃；玩家必须实际抢铃。下一名玩家可以在保护时间结束后继续翻牌，可能覆盖并消除当前机会。

### 7.2 `ring_bell`

```json
{
  "revision": 19,
  "boardEpoch": 13,
  "inputMethod": "keyboard"
}
```

`inputMethod` 仅用于无障碍与质量统计，不能影响排序。关键校验：调用者是玩家而非观众、`status=eligible`、阶段仍为 `playing`、`boardEpoch` 与当前桌面一致。铃请求不要求 `revision` 完全相等，只要 `boardEpoch` 相等且同一桌面尚未结算；这样普通连接状态更新不会无端使抢铃失效。

返回结果必须区分：

- `CORRECT_BELL`：正确并已收牌；
- `WRONG_BELL`：错误并已罚牌／结束；
- `STALE_BOARD`：所见牌面已经改变，不处罚；
- `BELL_ALREADY_RESOLVED`：同一桌面已有更早请求，不处罚；
- `NOT_ELIGIBLE`：观众、已退出者或房间外调用。

### 7.3 `resign`

退出策略与大厅公共生命周期对齐。首版建议将玩家标为 `resigned`，不再翻牌或抢铃；其现有明牌保持到下一次收牌，抽牌堆在游戏结束前仍归其所有且不得转交。若人数不足以继续，按 `player-exit` 结束并记录所有剩余持牌数。

## 8. “恰好五个”算法

只读取每个非空 `discardPile` 的末项：

```text
totals = { banana: 0, strawberry: 0, lime: 0, plum: 0 }
for player in players:
    if player.discardPile is not empty:
        top = catalog[player.discardPile[-1]]
        totals[top.fruitId] += top.fruitCount
validFruitIds = sorted(fruit for fruit, total in totals if total == 5)
isCorrectBell = validFruitIds is not empty
```

必须使用 `== 5`，不能使用 `>= 5` 或 `% 5 == 0`。已淘汰玩家尚未被收走的明牌堆仍参与计算；空堆不贡献数值。缓存结果必须与独立复算一致，否则事务回滚并记录内部错误。

## 9. 抢铃并发与公平

### 9.1 原子仲裁

每个房间使用单写锁或数据库比较交换：

1. 读取当前 `boardEpoch` 和尚未结算标记；
2. 第一个匹配请求写入唯一 `resolutionId`；
3. 在同一事务中完成正确／错误分支；
4. 提交后广播新 revision；
5. 后到请求根据 epoch 或 resolution 结果无副作用拒绝。

不要先广播“某人按铃”再异步判定，否则多个进程可能重复收牌或罚牌。

### 9.2 网络现实

纯网络游戏无法复制实体桌上的绝对同时性。本方案采用可审计的服务端到达顺序，不接受客户端声称的按键时间。建议：

- 生产房间固定到单一地区和单一权威进程；
- 翻牌后统一设置 350 ms 最短下一翻牌保护，所有人仍能立即按铃；
- UI 显示平滑后的 RTT 档位，不显示伪精确名次毫秒差；
- RTT 长期过高时提示改用休闲房，不暗中做延迟补偿；
- 排位赛若未来需要延迟补偿，应另行设计带签名的服务器时钟协议并经过对抗测试。

### 9.3 动画约束

服务端提交翻牌即改变 `boardEpoch`。客户端可以播放 180 ms 翻转，但卡面、计数和铃按钮在同一渲染帧可用；不能等动画结束才允许按铃。减少动态模式直接淡入。

## 10. 正确铃、误按与资格

### 10.1 正确铃

1. 保存结算前是否已经 `finalDuelArmed`。
2. 按确定顺序收集全部 `discardPile`。
3. 清空所有明牌堆，把收集牌追加到赢家抽牌堆底。
4. 标记所有“抽牌堆为 0 且明牌已被收走”的非赢家为 `eliminated`。
5. 赢家必然重新成为 `eligible`，并成为下一翻牌者。
6. 递增 `boardEpoch`，复算合计为全 0。
7. 若结算前最终二人标记已为真，进入终局；否则根据结算后人数决定是否刚刚武装最终二人阶段。

### 10.2 非最终阶段误按

1. 目标是除误按者外的全部 `eligible` 玩家，按误按者左侧起顺时针排序。
2. 从误按者抽牌堆顶依次移 1 张到每名目标抽牌堆底，最多一圈。
3. 不改变任何明牌堆，因此不递增 `boardEpoch`。
4. 若误按者抽牌堆为 0，则立即标记 `wrong-bell-empty`，失去抢铃资格；其明牌仍留桌上。
5. 重新选择下一名有牌可翻者；若当前指针仍合法则保持。
6. 结算后人数若刚降到 2，武装最终二人阶段，但本次误按本身不是最后铃。

### 10.3 最终二人误按

对手取得所有明牌，跳过普通罚牌，随后结束并计数。若出现超过两名 `eligible` 却错误设置 `finalDuelArmed`，不变量检查必须阻止提交。

## 11. 终局与活性

### 11.1 卡牌计数

每名玩家的最终持牌数为 `len(drawPile) + len(discardPile)`；正常最后铃后所有 `discardPile` 应为空。所有玩家合计必须始终为 56。

默认档案取最高数玩家为 `winnerIds`，允许多人。延长档案只在单人持有 56 张时正常结束。

### 11.2 无进展安全阀

每次翻牌、罚牌或淘汰后运行：

```text
canAnyoneFlip = any(eligible player has draw cards)
canAnyoneRingCorrectly = validFruitIds is not empty
```

若两者均为假，启动 10 秒 `noProgressDeadline`。期间玩家仍可误按或离开；状态变化即取消。截止时按当前总持牌数结束，原因 `no-progress`，并在结果页明确说明这是数字安全裁决。该边界不可悄悄伪装为官方正常终局。

## 12. 安全视图与回放

`view(room, viewer)` 必须重新构造对象，不能浅拷贝权威状态后删字段。

| 数据 | 玩家 | 观众 |
| --- | --- | --- |
| 每家抽牌张数 | 可见 | 可见 |
| 抽牌实例和顺序 | 不可见，包括自己 | 不可见 |
| 每家最上方明牌 | 可见 | 可见 |
| 明牌堆张数 | 可见 | 可见 |
| 被覆盖牌的完整列表 | 实时视图不可见 | 实时视图不可见 |
| 四种水果当前合计 | 忠实模式不下发；非排位计数辅助开启时才下发 | 同左 |
| 当前翻牌者、资格、最终二人标记 | 可见 | 可见 |
| 服务端 RNG、锁和精确接收时间 | 不可见 | 不可见 |
| 可执行动作 | 仅本人布尔值 | 全 false |

完成后的公共回放可以包含所有曾公开的翻牌、收牌、罚牌和判定事件，但不能包含未来牌序、随机种子或可逆推出牌序的数据。重连只需要当前顶牌、堆高、资格和最近事件，不应把整叠被覆盖牌自动展开成记牌器。

## 13. 前端实现

`GameView.vue` 只编排场景和调用宿主动作，规则结果全部来自服务端。

- 所有 2-6 名玩家的顶牌必须同时在一屏可见；禁止轮播或需要滚动才能看到某家牌。
- 中央铃始终固定，触摸目标至少 64 × 64 CSS 像素，建议桌面 112、手机 88。
- 本人抽牌堆和“翻牌”按钮只在轮到本人且达到最早翻牌时间时可用。
- 顶牌同时显示水果形状、大号数量和中文短名；忠实模式不显示自动合计或答案高亮。
- 资格状态至少使用“可翻牌／仅可抢铃／已退出”文字，不只改变透明度。
- `ring_bell` 可由点击、触摸和 Space 触发；长按、双击、键盘重复事件必须去抖为同一 epoch 一次请求。
- 请求提交后可以显示本地按下反馈，但不得先显示“抢到”；只有服务端结果才能显示赢家。
- 最近一次结算横幅应明确区分“正确抢铃”“误按罚牌”“旧牌面未受理”和“已被抢先”。

详细布局见 `docs/SCENE_MODEL.md` 和 `model/scene-catalog.json`。

## 14. 超时、断线和重连

- 当前翻牌者超时：休闲房在 8 秒后由服务器自动翻牌；排位房可在多次超时后判定离开。
- 抢铃永不由机器人替玩家自动提交。
- 断线玩家短暂保留资格；若轮到其翻牌，使用同一超时流程。
- 重连视图带当前 `boardEpoch`、`earliestNextFlipAt` 和该玩家动作布尔值。
- 客户端重复发送相同 `actionId` 时返回第一次结果，不重新结算。
- 进程恢复若发现 `phase=resolving_bell`，依据持久化 `resolutionId` 完成或回滚同一事务，绝不能二次收牌。

## 15. 不变量

每个原子动作后至少验证：

- 恰有 56 个已知实例 ID，且每张只出现一次。
- 每种水果 14 张，牌面副本分布为 `5/3/3/2/1`。
- 玩家座位唯一且覆盖 `0..n-1`，人数为 2-6。
- `discardPile` 末项才是顶牌；缓存的水果合计等于逐顶牌复算。
- `validFruitIds` 恰好是合计为 5 的水果集合。
- `currentPlayerId` 为空或指向 `eligible` 且抽牌堆非空的玩家。
- `eliminated/resigned` 玩家不能翻牌或按铃。
- `eligible` 且抽牌堆为 0 的玩家必须仍有明牌堆；否则应已淘汰。
- `finalDuelArmed=true` 只允许在默认档案且在局人数不多于 2。
- `finished` 必须有结果，非 `finished` 不得有最终胜者。
- 所有胜者 ID 属于玩家，分数之和为 56，最高分和平手逻辑一致。
- 安全视图递归不存在 `drawPile`、`discardPile`、`rng`、`seedSecret`、`receivedAtNs`。

## 16. 测试矩阵

### 16.1 牌库与准备

- 20 种唯一牌面、56 个实例、四种水果和每种副本分布精确。
- 2-6 人 round-robin 发牌全部用完，各家差不超过 1。
- 固定种子和 `dealOffset` 可复现；不同种子不假定必然不同。

### 16.2 翻牌与计数

- 第一次翻牌、新牌覆盖旧牌、被覆盖牌不计数。
- 单张 5、2+3、1+1+3、两种水果同时为 5。
- 4、6、10 不触发；混合水果合计 5 不触发。
- 覆盖使 8 降为 5 时触发。
- 空牌玩家跳过，其遗留顶牌继续计数。

### 16.3 铃与并发

- 正确铃收所有明牌、放赢家牌底、赢家继续。
- 普通误按给每个其他在局玩家一张，顶牌和 epoch 不变。
- 罚牌不足的顺时针短付与淘汰。
- 同 epoch 两到六个并发请求只产生一次结算。
- 后到旧 epoch 返回 stale 且不罚；伪造客户端时间不影响结果。
- 锁重试、重复 `actionId` 和恢复不重复收牌。

### 16.4 资格与终局

- 最后一张翻出后仍可抢铃；正确则复活，被收走／误按则退出。
- 从三人降到两人的当前铃不结束，下一铃才结束。
- 两人开局第一铃结束；最终二人误按由对手收明牌。
- 卡牌最多者、多人平手、`complete_collection` 56 张终局。
- 无人能翻且无有效铃时触发 `no-progress` 并清楚标记。

### 16.5 安全与界面

- 每名玩家和观众视图都不含任何抽牌身份或顺序。
- 实时视图不展开被覆盖明牌；赛后回放只含历史公开事件。
- 320、375、390、768、1024、1440 px 下 2-6 家顶牌同时可见且页面无横向滚动。
- Space、触摸、鼠标同路径；重复键、长按和双击每 epoch 最多一请求。
- 减少动态、高对比和屏幕阅读器状态可用。

### 16.6 完整对局仿真

对两种档案和所有人数运行大量固定种子机器人局。每一步检查牌张守恒、合法当前玩家、计数缓存、有限进展和终局总分；对默认档案验证最后铃规则，对延长档案验证 56 张或 `no-progress` 终止。

## 17. 战绩与观战

`record_state()` 保存：规则档案、玩家座次、服务端地区、每次翻牌公开牌面、铃判定、罚牌张数、资格变化、最终持牌数、结束原因和胜者。可保存匿名化 RTT 档位用于质量分析，但不能让其重排胜负。

不得保存或公开未翻牌顺序、RNG 种子、能够复原未来牌序的随机流，或其他玩家不可见的网络诊断明细。观众完全只读，不能调用 `flip_card`、`ring_bell` 或影响超时。

## 18. 分阶段里程碑

1. **M0 模型冻结**：牌表、Schema、状态机、场景引用和样例全部通过校验。
2. **M1 规则核心**：发牌、翻牌、计数、正确／错误铃、收牌与资格。
3. **M2 实时仲裁**：房间锁、epoch、幂等键、并发测试和恢复测试。
4. **M3 终局**：最终二人、延长玩法、平手、退出和无进展安全阀。
5. **M4 安全视图**：玩家／观众、重连、公开回放边界。
6. **M5 前端可玩**：2-6 人响应式桌面、键盘／触摸、减动效和结果页。
7. **M6 发布验收**：压力仿真、真实多地区网络测试、版权确认、生产构建和大厅注册。

## 19. 完成定义

只有当 56 张牌守恒、两种终局档案、所有 2-6 人布局、同 epoch 并发唯一结算、过期铃无误罚、空牌待救、断线重连、安全视图、随机仿真和目标视口全部通过，并且内置帮助与本规则书一致时，才视为可以申请加入游戏大厅注册表。
