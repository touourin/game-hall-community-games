# 《情书》数字实现方案

## 1. 范围与原则

首版目标是在 `game-hall` 插件 API v1 上实现 2–4 人、服务端权威、可重连的《情书》皇后扩展规则。默认 `queen_22` 在官方现行 21 张牌组中加入皇后 7.5 ×1；同时保留 `current_21` 和 `classic_16` 对照档案。三个档案统一在牌效完成后于牌堆仅余 1 张时结算，封存牌永不公开。

核心原则：

- 服务端保存全部牌序、手牌和私密知识，客户端只接收安全视图。
- 所有动作携带 `revision` 与一次性 `choiceId`，过期请求不产生部分修改。
- 洗牌、首家、平局首家和超时选择只使用服务端 RNG；测试可注入固定种子。
- 一次玩家动作以及由它触发的效果链必须事务化。
- 规则档案在开局时锁定并进入战绩，不允许中途改变。
- 前端不能自行判断命中、比较、合法目标或轮末，只负责呈现服务端结果。

## 3. 权威领域状态

`model/game-state.schema.json` 是序列化边界。运行时可以使用 dataclass，但字段语义应保持一致。

### 3.1 整局字段

- `profileId`：默认 `queen_22`，或官方对照 `current_21`、`classic_16`。
- `status`：`setup | active | finished`。
- `revision`：每个成功原子动作递增，拒绝旧客户端写入。
- `roundNumber`、`turnNumber`、`eventSeq`：分别驱动规则、并发校验和动画去重。
- `players`：固定座次、好感标记、本轮状态、手牌、公开出牌与保护。
- `gameWinnerIds`：整局结束后可含多人。
- `rngCommitment`：可选的种子承诺或随机会话 ID；不得进入普通视图。

### 3.2 本轮字段

- `deck`：有序实例 ID 数组，末端或首端的抽牌约定必须固定。
- `reserveCardId`：暗置牌；被王子取走后为 `null`。
- `faceUpSetAside`：两人局公开的三张实例 ID。
- `currentPlayerId`、`startPlayerId` 与 `phase`。
- `pendingChoice`：目标、猜测、大臣保留／牌底排序等一次性选择。
- `privateKnowledge`：服务端私密知识账本，只由 `view()` 按观察者过滤。
- `roundWinnerIds`、`rewardDeltas` 与 `endReason`：仅轮末存在。

### 3.3 牌实例

角色目录定义牌种；每轮生成稳定实例 ID，例如 `guard-01`、`queen-01`。所有实例必须且只能位于以下一个区域：牌堆、暗置区、两人公开移除区、某玩家手牌或某玩家公开出牌区。

不要把“淘汰弃牌”放入独立、不带归属的公共弃牌堆。官方要求打出和弃掉的牌都保持公开，而按玩家分区能让计牌和回放更清楚。

## 4. 状态机

完整转换表在 `model/state-machine.json`。建议阶段如下：

1. `round_setup`：建立牌组、暗置、两人公开移除、发牌、确定首家。
2. `turn_draw`：移除当前玩家保护，等待或自动执行抽牌。
3. `turn_play`：玩家持有两张牌，按伯爵夫人与皇后规则生成合法出牌。
4. `effect_choice`：等待目标、卫兵猜测或王子目标。
5. `chancellor_choice`：仅行动者看到候选，提交保留牌和牌底顺序。
6. `effect_resolution`：服务端原子移动牌、更新知识、保护或淘汰。
7. `round_end`：确定轮胜者、间谍资格与奖励。
8. `between_rounds`：展示结果，等待房主／自动开始下一轮。
9. `finished`：整局只读。

`effect_resolution` 通常不暴露为需要输入的 UI 阶段，但保留在状态机中，便于事务、动画和重连。

## 5. 动作协议

所有动作都至少包含 `revision`。服务端验证房间成员、当前阶段、行动者、负载类型、选项归属和 `choiceId` 后才修改状态。

### 5.1 `draw_card`

```json
{ "revision": 17 }
```

仅 `turn_draw` 的当前玩家可调用。移除自身侍女保护、从牌堆抽一张、转入 `turn_play`。也可在服务端内部自动调用，但 UI 显式抽牌能保留桌游节奏。

### 5.2 `play_card`

```json
{ "revision": 18, "cardInstanceId": "guard-03" }
```

验证牌在本人手中，并通过 `legal_play_ids()` 强制伯爵夫人或皇后。牌立即公开进入本人的出牌区，然后由效果解释器执行：无选择的效果直接完成；有选择的效果生成 `pendingChoice`。

### 5.3 `resolve_choice`

卫兵示例：

```json
{
  "revision": 19,
  "choiceId": "choice-r2-t6-guard",
  "targetPlayerId": "p3",
  "guessedCardTypeId": "princess"
}
```

大臣示例：

```json
{
  "revision": 27,
  "choiceId": "choice-r3-t2-chancellor",
  "keepCardInstanceId": "baron-01",
  "bottomOrder": ["spy-02", "prince-02"]
}
```

服务端只接受创建该选择时下发给该行动者的实例集合，并再次计算合法目标。`bottomOrder` 必须无重复且恰好覆盖所有未保留候选。

### 5.4 `next_round`

```json
{ "revision": 31 }
```

仅 `between_rounds` 使用。多人轮胜时先由服务端从 `roundWinnerIds` 中随机选下一轮首家，再洗牌发牌。房间也可以在展示最短时长后自动进入下一轮。

### 5.5 `resign`

退出或弃权策略必须与大厅统一。建议将玩家标为本轮淘汰并在后续轮次继续跳过；若活跃房间人数降到 1，则按 `forfeit` 原因结束整局。不要把离开玩家的隐藏手牌转交他人。

## 6. 合法出牌与目标生成

### 6.1 伯爵夫人约束

```text
if hand contains countess and (king or prince):
    legal plays = [countess]
else:
    legal plays = all cards in hand
```

这个检查只发生在 `turn_play`，不应用于大臣效果的保留选择，也不应用于王子强制弃牌。

### 6.2 皇后约束

```text
if hand contains queen and (king or countess):
    legal plays = [queen]
else:
    continue with countess constraint and ordinary choices
```

皇后约束只在 `queen_22` 生效，也只检查正常 `turn_play`。两张手牌不可能同时触发互相冲突的皇后与伯爵夫人结论；实现仍应把皇后检查和伯爵夫人检查写成统一约束集合，若未来扩展到三张正常手牌时可检测冲突并拒绝配置。

### 6.3 目标集合

- `other`：仍在局、不是行动者、未受侍女保护。
- `any`：仍在局的行动者本人，加上未受保护的其他仍在局玩家。
- 卫兵、牧师、男爵、国王和皇后使用 `other`。
- 王子使用 `any`；其他人全受保护时集合至少仍含行动者。
- `other` 为空时，牌已经打出但效果无效，直接进入轮末检查。

卫兵猜测候选为当前规则档案中实际存在的角色牌种，排除卫兵。客户端可显示该角色已公开数量，但命中判断必须在服务端。

## 7. 效果解释器

按 `card-catalog.json` 的 `opcode` 分派，避免按中文名称写条件。

| opcode | 服务端步骤 |
| --- | --- |
| `record-spy` | 公开牌照常入出牌区；轮末从历史推导唯一仍在局资格者 |
| `guess-hand` | 选择合法其他玩家和非卫兵角色；匹配则淘汰目标，皇后命中例外见下文 |
| `peek-hand` | 给行动者写私密知识事件，不改变目标手牌 |
| `compare-hands` | 给双方写私密牌面事件；低点者淘汰，相同无事 |
| `grant-protection` | 设置 `protected=true` 与开始回合时的到期语义 |
| `force-redraw` | 公开弃掉目标手牌；公主则淘汰，否则在不触碰最后 1 张牌的前提下从牌堆或暗置区补牌 |
| `draw-keep-bottom` | 抽 `min(2, max(0, deckCount - 1))`；建立仅行动者可见的有序选择 |
| `trade-hands` | 原子交换两个单牌手牌，并使相关旧知识过期 |
| `queen-guess` | 先由合法出牌生成器处理皇后强制；打出后复用卫兵式目标与猜牌 |
| `countess-constraint` | 没有即时效果；合法出牌生成器负责约束 |
| `eliminate-self` | 当前玩家立即淘汰，不再保留手牌 |

### 7.1 卫兵命中皇后

`guess-hand` 命中后先读取目标牌种，而不是直接淘汰：

```text
if profile == queen_22 and target card type == queen:
    publicly discard queen with reason guard-hit
    draw replacement from deck only when deckCount > 1, else reserve
    keep target active
else:
    eliminate target
```

弃掉皇后不执行 `queen-guess`。补牌绝不使用牌堆最后一张；若牌堆仅余 1 张则使用暗置牌，随后统一轮末检查。这个替代结果只由卫兵 opcode 触发，王子、淘汰清手和轮末亮牌都不触发。

### 7.2 弃牌触发

给所有公开牌移动记录 `reason`：`played | prince | guard-hit | eliminated | round-reveal`。普通角色只在 `played` 时执行牌效；公主在 `played` 或 `prince` 时淘汰持有者；间谍在 `played` 或 `prince` 时登记，但资格仍要求轮末在局；皇后只有 `guard-hit` 才触发防卫重抽。

当玩家因卫兵、男爵或主动打出公主而淘汰时，其剩余手牌以 `eliminated` 公开，不递归执行公主或其他即时牌效。这样避免淘汰流程产生二次动作链。

### 7.3 大臣事务

大臣打出后，把至多两张牌临时移入 `pendingChoice.privateCardIds`，而不是先写入普通安全视图的手牌。提交后一次性完成：

1. 校验保留和牌底顺序；
2. 令手牌只含保留牌；
3. 按约定方向把其余牌压到牌底；
4. 清空选择；
5. 检查轮末。

断线重连时，仅行动者视图恢复候选实例；其他人只看到“正在处理大臣”和候选数量。

## 8. 轮末流水线

效果事务完成后统一调用 `advance_or_finish_round()`：

1. 计算 `activePlayerIds`。
2. 只剩一人时，将其写入 `roundWinnerIds`，原因 `last-player`。
3. 否则牌堆张数小于等于 1 时，保持最后 1 张牌隐藏，比较仍在局玩家的单张手牌点数，将全部最高者写入 `roundWinnerIds`，原因 `one-card-left`。
4. 未结束（牌堆多于 1 张）才选择顺时针下一名仍在局玩家，增加 `turnNumber`，进入 `turn_draw`。
5. 已结束则给每名轮胜者 `+1`。
6. 在仍在局玩家中查找本轮曾 `played` 或被王子 `discarded` 间谍的人；恰好一人时再 `+1`。
7. 一次性应用 `rewardDeltas`，再按人数阈值计算所有 `gameWinnerIds`。
8. 有整局胜者进入 `finished`，否则进入 `between_rounds`。

间谍奖励、平局奖励和整局阈值不可在前端分步猜测，否则动画中途重连容易出现不同结果。

## 9. 隐藏信息与安全视图

`view(room, viewer)` 是唯一出站边界，按 `model/view-state.schema.json` 构造新对象，不得对权威状态做浅拷贝后删字段。

| 数据 | 本人 | 其他玩家 | 观众 |
| --- | --- | --- | --- |
| 自己手牌 | 实例、角色、点数完整可见 | 只见张数 | 只见张数 |
| 大臣候选／牌底顺序 | 仅行动者可见 | 只见处理阶段和数量 | 同左 |
| 牧师查看结果 | 仅查看者可见 | 不可见 | 不可见 |
| 男爵比较牌面 | 比较双方可见 | 只见结果／淘汰 | 只见结果／淘汰 |
| 暗置牌 | 不可见 | 不可见 | 不可见 |
| 牌堆身份与顺序 | 不可见 | 不可见 | 不可见 |
| 两人公开移除牌 | 可见 | 可见 | 可见 |
| 已打出／弃掉的牌 | 可见 | 可见 | 可见 |
| RNG 状态 | 不可见 | 不可见 | 不可见 |

视图必须由测试递归扫描，禁止出现 `deck`、`reserveCardId`、`rngState`、他人 `hand` 实例或非本人 `privateCardIds`。

## 10. 并发、重连与超时

- 每次动作校验 `revision`；成功后只递增一次。
- `pendingChoice.choiceId` 一次性消费；重复、旧轮次或非行动者提交均拒绝。
- 操作在权威状态副本上执行，全部不变量通过后才替换房间状态。
- `eventSeq` 为动画事件单调编号；客户端重连只播放大于已确认编号的事件。
- 玩家在 `turn_draw` 超时：自动抽牌。
- 玩家在 `turn_play` 超时：从合法出牌中用服务端 RNG 选择。
- 普通目标／猜测超时：从稳定排序的合法集合随机选。
- 大臣超时：随机保留一张，再随机排列其余牌底顺序。
- 超时行为写入公开事件，但不能公开被选择前看到的隐藏候选。

## 11. 前端实现

`GameView.vue` 只编排场景和调用宿主动作；卡牌、座位、选择、私密信息与轮末结果拆成组件。

- 自己的手牌固定在底部中心，最多三张（大臣阶段）。
- 公共牌堆、暗置牌数量标记和本轮状态居中。
- 每名玩家的公开出牌区按时间排列，支持展开计牌。
- 当前玩家、侍女保护、已淘汰和好感标记必须同时有图标与文字，不能只依赖颜色。
- 选择面板只消费服务端 `pendingChoice.options`；提交后立即锁定，等新 revision。
- 牧师／男爵私密牌面以可关闭浮层显示，日志中保留“当时看到”的标记。
- 大臣面板明确区分“保留”与“牌底先后”，并提供键盘排序。
- 320px 宽度下页面本身不得横向溢出；公开出牌历史可在区域内横向滚动。

详细区域和动画见 `docs/SCENE_MODEL.md` 与 `model/scene-catalog.json`。

## 12. 不变量

每个原子动作后至少校验：

- 当前档案牌实例总数等于 22、21 或 16，实例 ID 唯一。
- 每张实例恰处于一个区域，没有丢牌或重复牌。
- 每名仍在局玩家在普通阶段恰有 1 张手牌；`turn_play` 为当前玩家 2 张；大臣选择可临时 2–3 张。
- 已淘汰玩家没有隐藏手牌、没有保护、不是当前玩家或选择目标。
- 保护玩家不出现在其他玩家效果的候选目标中。
- 伯爵夫人约束下不接受国王或王子出牌；皇后约束下不接受国王或伯爵夫人出牌。
- `pendingChoice` 只存在于需要输入的阶段，行动者仍在局且与当前玩家一致。
- 轮末奖励总量等于轮胜者数，加上 0 或 1 枚间谍奖励。
- `gameWinnerIds` 只含达到阈值的玩家。

## 13. 测试矩阵

### 13.1 准备与牌张

- 22 张皇后扩展、21 张官方现行版与 16 张经典版的数量和逐角色副本精确。
- 2 人暗置 1、公开移除 3、发牌 2；3–4 人不公开额外移除。
- 固定种子下洗牌、首家和下一轮首家可复现。

### 13.2 十一种角色

- 卫兵命中、未命中、禁猜卫兵、无合法目标。
- 牧师私密查看及目标换牌后的知识过期。
- 男爵高／低／平手、比较后只剩一人。
- 侍女生效、跨回合、本人回合开始到期、全员受保护。
- 王子选自己／他人、牌堆抽牌、仅余 1 张时暗置补牌、公主淘汰、间谍登记、封存牌不泄漏。
- 大臣抽 2／1／0、始终留下 1 张封存牌、保留、牌底两种顺序、非法重复 ID、断线恢复。
- 国王交换与旧知识失效。
- 皇后搭配国王／伯爵夫人的强制出牌、猜中／未中、无目标；卫兵命中皇后后从牌堆或暗置牌重抽且不淘汰。
- 伯爵夫人搭配国王、两张王子之一、无强制、自愿打出、大臣不触发。
- 公主主动打出、王子弃掉与淘汰清手。
- 间谍唯一／多人／已淘汰／同人两张／与轮胜叠加。

### 13.3 轮末和整局

- 仅剩一人优先于空牌堆比较。
- 牌堆仅余 1 张时单胜、多人平局、淘汰者不参与且封存牌不公开。
- 2–4 人阈值；平局与间谍导致多人同轮达标。
- 下一轮首家只从轮胜者中选，不含仅获间谍奖励者。

### 13.4 安全

- 每个玩家和观众视图递归检查无牌堆、暗置牌和 RNG 泄漏。
- 大臣候选仅行动者可见；牧师仅查看者可见；男爵仅双方可见。
- 伪造实例、目标、猜测、牌底顺序、`choiceId` 和旧 revision 全部失败且状态不变。

### 13.5 完整对局仿真

对三个档案和全部合法人数运行大量固定种子机器人局。每步检查牌张守恒、阶段可推进、选择有限、轮次必然结束；最终 `player_result()` 与好感标记独立复算一致。

## 14. 战绩与回放

`record_state()` 仅保存可公开复核的信息：规则档案、人数、逐轮首家、公开移除牌、公开出牌／弃牌、淘汰原因、轮胜者、奖励分项、最终好感标记和胜者。

不要保存牌堆未来顺序、暗置牌未公开身份、大臣私密候选／牌底顺序、牧师查看结果或可逆推出这些内容的 RNG 种子。若未来实现完整私密回放，应使用每位玩家独立加密的数据流，而不是扩大公共战绩。

## 15. 分阶段里程碑

1. **M0 模型冻结**：Schema、牌表、场景引用和样例全部通过校验。
2. **M1 核心轮次**：卫兵至公主及皇后扩展全部效果、保护、淘汰和封存牌结算。
3. **M2 多轮整局**：好感标记、间谍奖励、阈值、平局与经典档案。
4. **M3 安全视图**：大臣、牧师、男爵的私密信息与重连完整覆盖。
5. **M4 前端可玩**：2–4 人响应式桌面、键盘操作、动画去重与结果面板。
6. **M5 发布验收**：随机仿真、浏览器矩阵、生产构建、版权确认与大厅注册。

## 16. 完成定义

只有当三个规则档案、所有目标人数、十一种角色、私密视图、超时重连、完整局仿真和目标视口全部通过，并且界面帮助、服务端裁决与本规则书一致时，才视为可以注册为大厅游戏。
