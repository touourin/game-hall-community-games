# 《璀璨宝石》卡牌与贵族建模

## 1. 模型目标

卡牌模型同时服务于规则引擎、网络快照、前端渲染、无障碍文本、测试和未来回放。它只描述玩法需要的身份、费用、奖励和威望，不把官方插画、人物肖像、Logo 或装饰边框视为规则数据。

完整机器目录位于 `model/card-catalog.json`，由 `model/development-cards.csv` 与 `model/nobles.csv` 通过 `scripts/generate_models.py` 生成。生成结果不应直接手改。

## 2. 数据依据与完整性

官方 2024 规则确认发展卡总数为 90，按等级为 40/30/20，但没有逐张列出费用。本包将实体卡图像转录数据与独立卡表统一字段后排序比较，90 个八元组全部一致。详细链接与方法见 `SOURCES.md`。

| 维度 | 1 级 | 2 级 | 3 级 | 合计 |
| --- | ---: | ---: | ---: | ---: |
| 卡牌数 | 40 | 30 | 20 | 90 |
| 每种奖励色 | 8 | 6 | 4 | 18 |
| 0 分卡 | 35 | 0 | 0 | 35 |
| 1 分卡 | 5 | 10 | 0 | 15 |
| 2 分卡 | 0 | 15 | 0 | 15 |
| 3 分卡 | 0 | 5 | 5 | 10 |
| 4 分卡 | 0 | 0 | 10 | 10 |
| 5 分卡 | 0 | 0 | 5 | 5 |
| 全部卡面威望 | 5 | 55 | 80 | 140 |

费用总量也具有固定分布：

- 1 级：总费用 3 的 10 张、4 的 15 张、5 的 15 张；
- 2 级：总费用 5 的 5 张、6 的 5 张、7 的 10 张、8 的 10 张；
- 3 级：总费用 7、10、12、14 各 5 张。

这些是数据验收信号，不是新的玩法规则。玩家仍按每张牌逐色支付。

## 3. 颜色与符号

| ID | 中文语义 | 建议符号 | 建议纹样 | 规则用途 |
| --- | --- | --- | --- | --- |
| `white` | 钻石 | `◇` | 点阵 | 费用、棋子、永久奖励 |
| `blue` | 蓝宝石 | `◆` | 波纹 | 费用、棋子、永久奖励 |
| `green` | 祖母绿 | `⬟` | 叶脉 | 费用、棋子、永久奖励 |
| `red` | 红宝石 | `⬢` | 人字纹 | 费用、棋子、永久奖励 |
| `black` | 缟玛瑙 | `●` | 交叉线 | 费用、棋子、永久奖励 |
| `gold` | 黄金百搭 | `★` | 放射纹 | 仅棋子与支付，不是奖励色 |

所有界面必须同时显示颜色名、符号或纹样中的至少两项。黑白卡面要用不同边框和文字标签，不能只靠背景亮度。

## 4. 稳定 ID

发展卡 ID：

```text
dev-{bonusColor}-{level}-{ordinal}
dev-white-1-01
dev-red-3-04
```

`ordinal` 只在“同奖励色 + 同等级”范围内稳定，不承诺对应官方印刷编号。ID 一旦进入战绩或回放就不可重排；改变数据应升级 `modelVersion` 并提供迁移。

贵族 ID 使用要求语义：

```text
noble-white-blue-4
noble-green-red-black-3
```

这样无需依赖不同版本中可能变化的贵族姓名与肖像，也能从 ID 判断是哪组奖励要求。

运行时保留牌另有实例级 `reservationId`。客户端针对保留区行动时传 reservation ID，不把隐藏 card ID 当作公共目标。

## 5. 发展卡语义结构

```json
{
  "id": "dev-blue-2-04",
  "kind": "development",
  "level": 2,
  "bonusColor": "blue",
  "prestige": 2,
  "cost": {
    "white": 2,
    "blue": 0,
    "green": 0,
    "red": 1,
    "black": 4
  },
  "totalCost": 7,
  "visual": {
    "framePattern": "blue-functional",
    "artworkSlot": "original-level-2-merchant-scene",
    "officialArtworkIncluded": false
  },
  "accessibility": {
    "labelZh": "2 级蓝宝石奖励发展卡，2 点威望；费用：钻石 2、红宝石 1、缟玛瑙 4",
    "compactLabelZh": "2级 蓝宝石 +1，2分"
  }
}
```

字段裁决：

- `cost` 固定含五个标准颜色键，0 也保留，便于逐色运算与 Schema 校验；
- `gold` 永远不能出现在卡面费用中；
- `totalCost` 是分析与校验字段，不能用于支付；
- `prestige` 为整数 0-5；
- 每张已购买卡固定提供 1 个 `bonusColor` 奖励；
- `visual` 只引用原创占位槽，不携带官方素材 URL；
- `accessibility` 由生成器从语义字段生成，避免视觉与播报不一致。

## 6. 贵族语义结构

```json
{
  "id": "noble-white-blue-green-3",
  "kind": "noble",
  "prestige": 3,
  "requirement": {
    "white": 3,
    "blue": 3,
    "green": 3,
    "red": 0,
    "black": 0
  },
  "requirementTotal": 9,
  "visual": {
    "portraitSlot": "original-neutral-patron-06",
    "officialPortraitIncluded": false
  }
}
```

十张贵族的结构约束：

- 5 张要求两个颜色各 4 个奖励，总要求 8；
- 5 张要求三个颜色各 3 个奖励，总要求 9；
- 每张固定 3 点威望；
- 要求只读取已购买发展卡，不读取棋子或保留牌；
- 每局只公开玩家人数 +1 张，其余移入服务端隐藏区域。

## 7. 卡牌区域模型

| 区域 | 顺序 | 身份可见性 | 可由何种动作移出 |
| --- | --- | --- | --- |
| `tiers[level].deck` | 有序 | 服务端私密；客户端只看数量 | `reserve_blind`，或市场补牌 |
| `tiers[level].market[slot]` | 固定槽 | 全公开 | `purchase_face_up`、`reserve_face_up` |
| `players[id].reservations` | 保留顺序 | 按来源决定 | `purchase_reserved` |
| `players[id].purchasedCardIds` | 获得顺序 | 全公开 | 基础规则不再移出 |

市场牌被购买或公开保留后，同一事务内从相同等级牌堆补位。盲保留只减少牌堆，不改变市场。牌堆空时槽位为 `null`，不得复制最后一张或跨等级补牌。

## 8. 保留牌模型

```json
{
  "reservationId": "reservation-p2-003",
  "cardId": "dev-black-2-04",
  "level": 2,
  "source": "deck",
  "knownToAll": false,
  "reservedAtAction": 18
}
```

安全视图规则：

- 持有者总能看到自己的真实 `cardId` 与完整卡面；
- `source = market` 时 `knownToAll = true`，所有视角继续看到 card ID；
- `source = deck` 时 `knownToAll = false`，其他玩家和观众收到 `cardId: null`，但可见 level；
- 公共日志不存盲保留 card ID；
- 对手提交 purchase 动作时没有任何路径引用这项 reservation ID。

保留牌上限由数组长度决定，最多 3 张。不能用删除动作清空。

## 9. 费用与支付模型

发展卡的实际费用是派生值，不写回目录：

```text
effective[c] = max(card.cost[c] - purchasedBonusCount[c], 0)
```

支付对象包含六色完整向量：

```json
{
  "white": 1,
  "blue": 1,
  "green": 0,
  "red": 0,
  "black": 1,
  "gold": 1
}
```

五色支付各自不能超过实际同色需求；黄金必须恰好等于剩余所有颜色需求之和。这个结构保留了玩家“即使有对应宝石也选择花黄金”的规则权利，同时可机械拒绝超付。

前端可以为每张卡缓存：

- `effectiveCost`：当前玩家的折扣后费用；
- `minimumGoldNeeded`：若优先花五色宝石，至少需多少黄金；
- `affordable`：持有棋子能否覆盖全部需求；
- `paymentBounds`：每色最大可付值与黄金最大值。

这些只是安全视图中的便利派生量，最终服务端仍从权威状态重算。

## 10. 卡面视觉模型

建议发展卡宽高比为 5:7，逻辑尺寸 `160 × 224`：

```text
┌────────────────────────┐
│ 威望 3       奖励 ◆ 蓝 │  顶部规则带：永远可见
├────────────────────────┤
│                        │
│   原创中性商路插画槽   │  不承载玩法信息
│                        │
├────────────────────────┤
│ ◇3  ⬟3  ⬢5  ●3       │  底部费用带：只列非零色
└────────────────────────┘
```

层级要求：

- 威望与奖励占卡面顶部 24%，在玩家牌列只露出顶部时仍可读；
- 费用区占底部 28%，颜色图标旁始终有数字；
- 等级可以用 1/2/3 个小菱形和文字双编码；
- 原创插画区不得覆盖任何数字；
- 市场缩小到 112px 宽时仍显示完整费用；更窄时改为结构化列表，不能只留颜色块。

贵族建议为 `180 × 180` 方形：左上威望、底部奖励要求、中部原创中性赞助人剪影。人物身份不参与规则，不应作为 aria 名称的唯一内容。

## 11. 牌背与隐藏态

需要三个功能牌背：1、2、3 级。牌背只表达等级，不复制官方颜色、纹章或版式。

- 使用显式文字“1 级／2 级／3 级”；
- 同时使用一个、两个、三个同形标记；
- 盲保留牌对手视图使用相应等级牌背；
- 牌背不显示随机种子、序号或可推断真实卡 ID 的纹理差异；
- 同等级每个实例使用完全一致的牌背资源。

## 12. 宝石棋子模型

虽然棋子不是卡牌，也应和卡牌颜色使用同一语义 ID。每个棋子显示颜色名首字、符号和纹样；黄金明确写“百搭”。

棋子是计数资源，不需要为每枚生成全局实例 ID。服务端用六色整数向量即可，但事件应记录变更前后或 delta，方便守恒复算。

## 13. 无障碍与本地化

完整卡牌播报模板：

```text
{level} 级{bonusName}奖励发展卡，{prestige} 点威望；费用：{nonZeroCosts}
```

贵族播报模板：

```text
贵族板块，3 点威望；拜访要求：{requirements}的永久奖励
```

要求：

- 顺序固定为白、蓝、绿、红、黑，便于对比；
- 0 费用在完整句中省略，在支付表中保留列；
- “奖励”“棋子”“费用”用词不混用；
- 颜色的中文显示名称来自本地化表，ID 不翻译；
- 市场卡操作名称要包含等级、奖励色和威望，不能只读“购买按钮”；
- 盲保留牌的 aria 文本对非持有者只能说“2 级隐藏保留牌”。

## 14. 校验要求

`scripts/validate_models.py` 至少验证：

- CSV 与生成 JSON 的 SHA-256 摘要一致；
- 90 张卡 ID 唯一、10 张贵族 ID 唯一；
- 等级 40/30/20，每种奖励色 8/6/4；
- 卡面威望、费用总量分布与本文件一致；
- 每张卡五色费用键完整且没有 gold；
- 贵族恰为五个 4+4、五个 3+3+3；
- 视觉引用全部以 `original-` 或功能模式命名，`officialArtworkIncluded` 恒为 false；
- 每个 accessibility label 与语义数值一致；
- 示例状态中的所有 card ID 和 noble ID 都存在；
- SVG 图集标记当前 `modelVersion`，并包含 90 个发展卡组和 10 个贵族组。

## 15. 权利边界

本模型可用于规则实现与原创 UI，但不能据此声称获得官方授权，也不应把它变成含官方插画的可印刷复刻套件。公开发布时应使用自行创作或已获许可的视觉资产，并对 Splendor 名称与产品识别元素完成独立审查。
