# 卡牌模型

## 1. 模型边界

`model/card-catalog.json` 是卡牌种类与任务内容的事实目录，不保存运行中卡牌位置。实际对局由服务端按目录创建唯一实例 ID，并在牌库、弃牌堆、公共市场和玩家手牌之间移动实例。

目录覆盖三组组件：

- 110 张车票牌；
- 46 张任务牌；
- 1 张语义上的欧洲快车奖励牌。

奖励牌不进入任何抽牌堆，只用于说明最长路线的 10 分奖励。

## 2. 车票牌类型

| 类型 ID | 中文标签 | 数量 | 可作为 |
| --- | --- | ---: | --- |
| `train-purple` | 紫色车票 | 12 | 紫色支付 |
| `train-blue` | 蓝色车票 | 12 | 蓝色支付 |
| `train-orange` | 橙色车票 | 12 | 橙色支付 |
| `train-white` | 白色车票 | 12 | 白色支付 |
| `train-green` | 绿色车票 | 12 | 绿色支付 |
| `train-yellow` | 黄色车票 | 12 | 黄色支付 |
| `train-black` | 黑色车票 | 12 | 黑色支付 |
| `train-red` | 红色车票 | 12 | 红色支付 |
| `train-locomotive` | 彩虹车票 | 14 | 任意基础色；渡轮最低支付；全彩虹隧道支付 |

`gray` 只用于版图上的中性轨道，不是一种车票牌。

## 3. 任务牌

每张任务牌有稳定 ID、两个无方向端点、分值与 `regular` 或 `long` 分类。端点顺序只用于稳定显示，不改变连通判断。

初始发牌从两个池分别进行：每人 1 张长程和 3 张短程。游戏进行中只抽剩余短程牌；未发出的长程牌不会加入短程牌库。

任务牌的背景色不作为规则字段。不同印次的背景配色不同，前端必须使用分类标签、图标与读屏文本共同表达 `regular` / `long`。

## 4. 实例化与唯一性

推荐实例 ID：

```text
train-red-01 ... train-red-12
train-locomotive-01 ... train-locomotive-14
ticket-regular-001 ...
ticket-long-001 ...
```

目录 ID 与实例 ID 分离：

```json
{
  "instanceId": "train-red-07",
  "typeId": "train-red"
}
```

任务牌本身每种只有一张，因此运行实例可以直接沿用目录 `id`。但代码仍应通过同一位置索引器检查“一张牌只能处于一个区域”。

## 5. 卡背与隐藏信息

### 5.1 车票牌

所有 110 张车票牌必须共用完全相同的卡背资源。暗牌的 DOM、缓存键、网络事件、动画时长和尺寸都不能根据颜色变化。

### 5.2 任务牌

所有任务牌暗置时共用同一张中性卡背。长程与短程的分类也属于秘密：对手只知道某玩家持有几张任务牌，不应从卡背、边框或资源地址判断类型。

### 5.3 安全视图

- 本人手牌：返回实例 ID 与类型；
- 对手手牌：只返回数量；
- 本人任务牌：返回 ID、端点、分值与完成预览；
- 对手任务牌：只返回数量；
- 观众：对所有玩家都采用对手规则；
- 终局：在 `result` 中公开任务牌和完成状态。

## 6. 视觉模型

原创占位资产由 `scripts/generate_models.py` 生成到 `assets/card-atlas.svg`。它只表达结构，不模仿官方插画。

### 6.1 车票牌

| 属性 | 建议值 |
| --- | --- |
| 逻辑画布 | 440 x 680 |
| 圆角 | 28 |
| 内容安全区 | 四边 36 |
| 主识别 | 高对比色带 + 唯一几何纹样 + 两字母码 |
| 彩虹牌 | 多段中性色谱 + 星形/放射纹 + `LOCO` 文本 |
| 卡背 | 单色压纹 + 公共铁路符号，不带类型信息 |

八种基础色同时分配独立纹样：圆点、横线、斜线、十字、菱格、波纹、方格、三角。色觉异常用户可凭纹样和文字识别。

### 6.2 任务牌

| 属性 | 建议值 |
| --- | --- |
| 逻辑画布 | 680 x 440 |
| 主内容 | 起点、终点、分值、分类标签 |
| 路线示意 | 抽象两节点连线，不使用官方版图截图 |
| 长程标识 | `LONG` 文本 + 双线边框，不只依赖底色 |
| 卡背 | 与所有任务牌相同的中性网格 |

## 7. 交互状态

每张本人车票牌可拥有以下派生状态，不能写回权威目录：

- `idle`：可浏览；
- `selected`：加入当前支付候选；
- `eligible`：可用于当前声明颜色；
- `ineligible`：不能用于当前支付；
- `locked`：隧道初始支付已提交，等待揭示或补付；
- `spent`：服务端确认后进入弃牌动画。

任务牌使用 `offered`、`kept`、`rejected`、`completed-preview`、`failed-preview` 与 `revealed-final`。其中完成预览只由服务端根据当前公开路线和本人的秘密任务计算，不能成为对外公开事件。

## 8. 支付选择体验

前端可以提供“自动选择”，但必须把具体 `cardIds` 提交给服务端。自动策略按以下顺序减少误用彩虹牌：

1. 尽量使用对应基础色；
2. 只在基础色不足时补彩虹；
3. 渡轮先预留必需的彩虹数量；
4. 隧道初始支付全彩虹是明确的特殊选择，需二次确认。

玩家仍可手动选择更多彩虹牌，因为保留哪种基础色具有策略意义。服务端不应擅自替换用户选中的合法牌组。

## 9. 无障碍

- 颜色名称始终出现在可访问名称中，例如“红色车票，第 2 张，共 12 张”；
- 图案码不能只作为装饰，缩小到 72 px 时仍可辨认；
- 选中状态同时使用边框、勾选图标和 `aria-pressed`；
- 公共市场变化通过 `aria-live="polite"` 播报；
- 彩虹牌作为公共第一张时，按钮文案提示“拿取后结束回合”；
- 键盘可在手牌、市场和任务候选之间移动，并可取消尚未提交的选择。

## 10. 数据关系

```text
card-catalog.json
├── trainCardTypes[9] -> 110 个运行实例
├── destinationTickets[46]
│   └── fromCityId / toCityId -> board-map.json cities
└── bonusCards[1]

game-state.schema.json
├── trainDeck / trainDiscard / faceUpMarket
├── players[].trainHand
└── players[].destinationTicketIds

view-state.schema.json
├── self.trainHand / self.destinationTickets
└── players[].trainHandCount / destinationTicketCount
```

`validate_models.py` 会检查 110 张车票牌的组成、46 张任务牌的分类、任务 ID 唯一性、城市引用、分值范围和所有端点不相同。

## 11. 版权边界

本模型不提供官方卡面、Logo、字体、装饰边框或可印刷复刻文件。正式产品可以继续使用同一规则与数据契约，但必须替换为已获授权或完全原创的主题、美术、名称和品牌表达。
